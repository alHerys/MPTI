## 1. What we are building

A small web app for micro F&B vendors (warung, cafe, street cart, home baker) that have **no sales history**. The vendor enters business info, a menu, and a few days of sales. The app recommends **how many portions of each product to produce tomorrow**, with a range (P10/P50/P90), a confidence label, and a plain-language reason. Recommendations improve as the vendor adds data (Day 0 → Day 3 → Day 7).

Core idea: borrow strength from a **reference dataset of similar businesses**, then update with the vendor's own data (Bayesian-style shrinkage), then choose the production quantity with a **cost-based newsvendor rule**.

## 2. Scale and scope

**In scope (MVP):**
- Single deployable web app, single database, server-rendered pages plus small vanilla JS.
- One demo login, three seeded demo businesses (0, 3, and 7 days of history, so all stages are demonstrable).
- Up to 50 products per business, up to 365 days of sales per product, CSV import up to 5,000 rows / 1 MB.
- Reference dataset: synthetic, ~24 businesses × 6 to 10 products × 90 days (≈15k rows), generated by a seeded script.
- Statistical model: numpy and scipy only.

**Size budget (a guide to prevent over-engineering):** backend ≤ ~1,500 LOC, ML ≤ ~400 LOC, ≤ 7 HTML templates, 1 CSS file, ≤ 3 small JS files, ≥ 40 tests.

**Explicitly out of scope:** multi-tenancy/self-registration, payments, weather/event feeds, POS/WhatsApp/GrabFood integration, deep learning (LSTM, GNN, diffusion), GPU, mobile native apps, i18n beyond Indonesian, admin panel, email, background workers, microservices, fairness audits, real customer data.

## 5. Specification of the model (implement exactly)

All constants in `app/ml/config.py`.

### 5.1 Reference data (T2.2)
`scripts/gen_reference.py --seed 42` writes `data/reference_sales.csv` (`series_id,date,qty`) and `data/reference_meta.csv` (`series_id,business_type,location_type,category,price,capacity_factor,base_mean,dispersion`). Generate each series as: `qty_t ~ NegBin(mean = base_mean × weekday_factor[category][dow] × noise, dispersion φ)`, 90 days. Vocabularies:
- business_type: `warung, cafe, gerobak, bakery, kantin`
- location_type: `kampus, kantor, permukiman, pasar`
- category: `nasi, mie, snack, minuman, roti`
- weekday_factor profiles per category (7 values around 1.0, e.g. kantin/kantor weaker on weekends). Choose plausible values, document them.

`data/README_data.md` (Indonesian) **must state that the data is synthetic**, how it is generated, the seed, and that it is not real vendor data. (WBS 2.2 criterion: "asal data dijelaskan".)

### 5.2 Cold-start prior, Day 0 (T3.1)
Given a product with `(business_type, location_type, category, price, capacity_factor)`:
1. Build a feature vector: one-hot of business_type, location_type, category + `log(price)` scaled to [0,1] by reference min/max.
2. Find the **k = 5** nearest reference series (Euclidean). If a business has the same category series, they naturally rank first.
3. Prior mean `μ0` = **weighted median** of neighbor mean daily sales (weights = 1/(distance+0.1)), multiplied by `capacity_factor / neighbor_capacity_factor` (default capacity_factor = 1.0 if the vendor does not give one).
4. Prior daily dispersion `φ_day` = median of neighbor dispersions (fallback `0.15`; clamp to [0.02, 1.0]).
5. Prior weekday profile = mean of neighbor weekday factors, normalized to mean 1.
6. Return `Prior(mu0, phi_day, weekday_profile, neighbor_ids, neighbor_distance_mean)`.

Empty reference or fewer than 5 series → use all available; zero series → `μ0 = 10`, `φ_day = 0.15`, flat profile, and flag `low_reference=True`.

### 5.3 Update with own data, H0/H3/H7 (T3.2)
Let `n` = number of days with recorded sales for the product, `ȳ` = mean of adjusted daily demand.
- **Stockout adjustment:** a day with `sold_out = true` uses `qty × 1.15` (constant `STOCKOUT_UPLIFT`). Sold-out days only lower-bound true demand. Document as a heuristic in the limitations.
- **Shrinkage weight:** `w = n / (n + K)` with `K = 4`.
- **Posterior mean:** `m = w·ȳ + (1−w)·μ0`.
- **Stage label:** `H0` if n < 3, `H3` if 3 ≤ n < 7, `H7` if n ≥ 7.
- **Weekday factor for target date:** reference profile factor `f_ref[d]`. If `n ≥ 7`, blend with own: raw `r_d` = mean(own adjusted qty on weekday d) / ȳ (only if that weekday has ≥1 observation), `f_d = f_ref[d] + (n_d/(n_d+3))·(r_d − f_ref[d])`. Otherwise `f_d = f_ref[d]`.
- **Target mean:** `m_target = max(m × f_d, 0.5)`.

### 5.4 Predictive distribution and quantiles (T3.3)
Negative binomial with mean `m_target` and effective dispersion
`φ_eff = φ_day + CV0² · K/(n+K)`, `CV0 = 0.40`.
- `r = 1/φ_eff`, `p = r/(r + m_target)`, distribution `nbinom(n=r, p=p)`.
- `P10 = ppf(0.10)`, `P50 = ppf(0.50)`, `P90 = ppf(0.90)` as integers.
- Enforce `0 ≤ P10 ≤ P50 ≤ P90` (apply `np.maximum.accumulate` as a safety net).
- Property to test: interval width must shrink (weakly) as `n` grows for the same data pattern.

### 5.5 Cost-based optimization, "alpha" (T3.4)
Newsvendor rule with per-product `price`, `unit_cost`, `salvage_value` (default 0):
- `Cu = price − unit_cost` (profit lost per unit short), `Co = unit_cost − salvage_value` (loss per unit left over).
- `alpha = Cu / (Cu + Co)`, clamped to [0.05, 0.95].
- `recommended_qty = ppf(alpha)` of the distribution above (exact quantile, integer).
- `nearest_band` ∈ {`P10`,`P50`,`P90`} = the standard quantile whose level is closest to `alpha`.
- Validation: `price ≤ unit_cost` → API returns 422 with a clear message (no sensible newsvendor). `Co = 0` → alpha = 0.95.
- Test examples: price 10000, cost 3000 → Cu 7000, Co 3000 → alpha = 0.70 → qty between P50 and P90; price 10000, cost 6000 → alpha = 0.40 → qty between P10 and P50; price 10000, cost 9000 → alpha = 0.10 → qty ≈ P10.

### 5.6 Explanation and confidence (T3.5)
Confidence label (Indonesian):
- Base by n: `rendah` (n<3), `sedang` (3≤n<7), `tinggi` (n≥7).
- `ratio = (P90 − P10) / max(P50, 1)`. If `ratio > 1.2` downgrade one level (floor `rendah`).
- If `low_reference` → force `rendah`.

`reasons` is a list of Indonesian strings built from templates, in this order, including only those that apply:
1. Stage: "Belum ada data penjualan; estimasi dari {k} usaha serupa." / "Berdasarkan {n} hari data Anda dan usaha serupa." / "Berdasarkan {n} hari data penjualan Anda."
2. Weekday: if `|f_d − 1| > 0.10`: "Hari {nama_hari} biasanya {lebih ramai/lebih sepi} (±{pct}%)."
3. Stockout: if any sold-out day in the data: "Ada hari kehabisan stok; permintaan disesuaikan naik {pct}%."
4. Cost: "Margin Rp{Cu} per porsi vs kerugian sisa Rp{Co}; target peluang cukup stok {alpha_pct}%."
5. Low confidence: "Keyakinan rendah; catat penjualan harian agar rekomendasi membaik."

### 5.7 Engine entry point (ties it together)
`engine.recommend(product, business, sales_rows, target_date, reference) -> Recommendation` (dataclass) containing: `stage, n_days, mean, p10, p50, p90, alpha, recommended_qty, nearest_band, confidence, reasons, neighbor_count`. Pure function, no DB access, fully unit-testable. The router loads data and calls it.

### 5.8 Evaluation (T3.7), `scripts/evaluate.py` → `docs/model_report.md`
Leave-one-business-out backtest on the reference dataset: for each held-out series and each stage (H0 uses 0 days, H3 uses first 3, H7 uses first 7), predict days after the cutoff (the next 14 days), using only the other businesses as the reference.
Metrics per stage: **WAPE**, **pinball loss** at 0.1/0.5/0.9, **P10–P90 coverage** (nominal 80%), and **newsvendor profit** relative to baselines.
Baselines: (a) global mean of all reference series, (b) at H3/H7 only, the mean of own data (no shrinkage).
Report (Indonesian) must include: table of metrics, the comparison with baselines, and a **Keterbatasan** section stating that (1) data is synthetic so the gains reflect the generator, not the real world; (2) stockout uplift is a heuristic; (3) no validation with real vendors. **Do not claim real-world accuracy.**
Acceptance (soft, report honestly even if missed): model WAPE at H0 ≤ global-mean baseline; H7 WAPE ≤ H0 WAPE; coverage within 0.65 to 0.92. If a criterion is missed, record the numbers in the report and a note in DECISIONS.md, but still mark the task done once the report is generated and reviewed for honesty.
